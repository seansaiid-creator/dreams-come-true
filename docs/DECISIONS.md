### 4개 창은 한 워크트리를 공유한다 — 공유 문서는 편집 즉시 커밋 (2026-09-04 신설)
전략·데이터·컨텐츠·개발 창이 **같은 디렉터리, 같은 `main` 브랜치**에서 동시에 작업한다. 워크트리는 하나뿐이다.
1. **공유 문서(`WORKLOG.md`·`DECISIONS.md`·`OPERATIONS.md`)는 편집한 즉시 커밋한다.** 미커밋 상태로 오래 들고 있으면 다른 창의 경로 지정 add에 섞여 들어간다(09-04 실제 발생: 컨텐츠창 `085e86d`이 개발창의 WORKLOG 편집을 삼킴).
2. **`git add -A` 금지만으로는 막을 수 없다.** 경로를 지정해도 *같은 파일*을 두 창이 동시에 만지면 섞인다.
3. **커밋 직전에 `git log --oneline -3`으로 다른 창이 방금 무엇을 넣었는지 본다.** 규칙·문서·스크립트를 **신설하기 전에도** 확인한다 — 09-04에 기록 규칙이 3중 사본이 될 뻔했다.
4. **커밋 전 `git diff --cached --stat`으로 내가 의도한 파일·줄 수만 올라갔는지 확인한다.** 예상과 다르면 커밋하지 말고 원인부터 본다.
5. 코드(HTML 143개·`saju/`·`scripts/`)는 개발창 전유다. 다른 창은 건드리지 않는다.

### GA4 당일 데이터로 판단하지 않는다 (2026-09-03 신설 — 이틀 연속 오진 후)
1. **당일·전일 데이터로 증감을 판단 금지.** GA4는 처리 지연이 있어 최근 시간대가 통째로 0으로 나온다.
   판단은 **최소 2일 지난 완성 데이터**로 한다.
2. **"같은 시각까지 누적" 비교도 안 된다.** 오늘분이 미처리면 그 비교 자체가 무의미하다.
   (2026-09-03에 이 방법으로 "-63% 급락"이라 잘못 결론냈다.)
3. **급락이 의심되면 이 순서로 검증한다:**
   ① 실시간 API(`runRealtimeReport`) — 처리 지연을 받지 않는 유일한 지표. 여기 사용자가 있으면 사이트는 정상
   ② 사이트 응답 200 + GA 태그 존재 확인
   ③ 배포 커밋 시각과 급락 시각 대조 — 시각이 안 맞으면 배포 탓이 아니다
   ④ 그래도 의심되면 **2일 뒤 완성 데이터로 재확인**
4. **`(not set)` / `(data not available)`은 오류가 아니라 미처리분**이다. 처리가 끝나면 제 유입원을 찾아간다.

> 계기: 9/2 "(not set) 25건 = 유입원 추적 손실"로 오진 → 다음날 조회하니 `네이버 33, (not set) 0`.

여러 번 포함하기 때문에 15가 반복해서 나온다. 이 숫자로 "노출이 강하다/약하다"를 말하지 않는다.

1. **유효한 것은 `>0`인지 아닌지뿐이다.** 헤드라인 `22/50`은 그 이진값이므로 그대로 유효하다.
2. **추적 검색어는 페이지 제목에서 뽑은 추정치다.** 실제 사용자 질의가 아니다.
   2026-09-04 실측: 노출 0으로 찍힌 페이지 4개에서 실제 유입이 발생했다
   (가방을 잃어버리는 꿈 6세션, 친구가 죽는 꿈·금 줍는 꿈·아기꿈 각 1).
   → 네이버 서치어드바이저 「리포트 → 콘텐츠 노출/클릭」의 실제 질의를 받아
   `scripts/recovery-targets.json`을 교체하기 전까지 `22/50`은 **참고치**다.
3. **노출 여부와 세션의 상관을 통계로 말하지 않는다.** 09-03 교차표는 노출O·세션O 8 / 노출O·세션X 14 /
   노출X·세션O 4 / 노출X·세션X 24 (n=50), 피어슨 r=0.076이었으나 **그날 총 세션이 26뿐이라
   대부분 칸이 0이다.** 표본이 이 규모인 동안 상관계수는 판정 근거가 되지 못한다.
4. **회복 판정의 1차 지표는 GA4 쪽에 둔다** — 스크래핑과 독립적이고 방향이 같은
   **"세션이 1회라도 발생한 랜딩페이지 수"**를 함께 본다. 단 **반드시 같은 길이의 기간끼리, 사용자 수로 정규화해** 비교한다(09-06 정정 — 7일 대 1일 비교로 무효 결론을 낸 적이 있다).
