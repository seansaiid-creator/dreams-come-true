# 전략창 핸드오프 — 꿈해몽 행운 (suksuki.com)

> ## 🟢 활성 — 단, 별도 창이 아니라 **운영·전략창(메인 세션)이 이 역할을 겸한다** (2026-09-04~)
> 전략 판단은 데이터가 근거이므로 데이터창과 붙여 운영한다(§0의 수렴 문제도 이렇게 하면 줄어든다).
> 전략 논의가 길어져 일일 추적이 묻히기 시작하면 그때 분리한다.


> 작성 2026-09-04. 이 창은 **무엇을 왜 언제 할지**를 정한다. 데이터·컨텐츠·개발 세 영역을 **하나의 방향으로 수렴**시키는 것이 이 창의 존재 이유다.
> 실행은 하지 않는다 — 배포는 개발창, 문안은 컨텐츠창, 일일 추적은 데이터창.

---

## 0. 이 창이 다른 창을 "볼 수 있는" 유일한 방법

**세션 간에 대화는 공유되지 않는다.** 데이터창에서 무슨 말이 오갔는지 이 창은 알 수 없다.
공유되는 것은 **레포 파일과 메모리뿐**이다. 그러므로:

| 알고 싶은 것 | 읽을 파일 |
|---|---|
| 각 영역의 현재 상태·대기 작업 | `docs/handoff/DATA.md` · `CONTENT.md` · `DEV.md` |
| 무슨 일이 있었나(사건·문제·교훈) | `docs/WORKLOG.md` |
| 이미 정해진 것·버린 것 | `docs/DECISIONS.md` |
| 운영 기준·KPI·전략 정본 | `OPERATIONS.md` |
| UI/UX 지적의 이행 여부 | `docs/UIUX_REVIEW.md` |
| 실측 수치 | `content-queue/recovery-log.json`, `scripts/recovery-baseline.json`, `scripts/ga/*` 직접 실행 |

**세션 시작 시 위 6개를 먼저 읽는다.** 이걸 건너뛰면 다른 창이 이미 해결한 문제를 다시 제안하거나, 이미 기각된 안을 다시 꺼내게 된다(2026-09-02~03에 실제로 발생).

**수렴이 깨지는 지점**: 어떤 창이 결론을 대화에만 남기고 파일에 안 적으면, 이 창은 그것을 영원히 모른다.
의심되면 `git log --since=... -- docs/` 로 각 핸드오프가 언제 마지막으로 갱신됐는지 확인하라. 활동은 있었는데 갱신이 없으면 그 창에 기록을 요청해야 한다.

## 1. 절대 규칙
- `OPERATIONS.md` **§0 대원칙** 최우선: 검색·실측으로 확인한 뒤 말한다 · **예측/추측 금지** · 객관적 판단만, 희망적 표현 금지
- **데이터 없이 방향을 정하지 않는다.** 이 프로젝트의 반복된 실패가 정확히 그것이다:
  - 사주 CTA를 스크롤 87% 지점에 배치 → 30일 클릭 **0건**(90% 도달률이 13%인 걸 안 보고 정함)
  - 도메인 전환 시 트래픽 하락 위험을 계산에 넣지 않음 → 9/3 사용자 **-59%**
- **전략은 결정되는 순간 파일에 들어간다.** 대화에만 있으면 없는 것과 같다(9/2 UI/UX 지적이 이렇게 유실됨 → `docs/UIUX_REVIEW.md` 신설 계기)
- 실행 지시는 **해당 창의 핸드오프 "대기 작업"에 적어** 전달한다. 이 창이 직접 코드·문안을 건드리지 않는다
- 운영자 컨펌 없이 방향을 확정하지 않는다(`OPERATIONS.md` §5)

## 3. 현재 전략 지형 (2026-09-04 기준, 전부 실측)

### 제약
| 항목 | 수치 |
|---|---|
| 기준선(전환 전 30일) | 일 사용자 **48.7** |
| 9/3 (전환 후 첫 완전일) | **22 (-55%)** |
| 유입 구성 | 네이버 모바일 **97%**, 상세 페이지 착지 95% |
| 세션당 페이지 | **1.26** — 두 번째 페이지로 안 넘어감 |
| 90% 스크롤 도달 | **13~14%** |
| 재방문율 | **0.2%** |
| 사주 진입 클릭(30일) | **0** (`saju_open` 10건은 전부 상단 네비 경유) |

### 확정된 방향
- **해자는 하나뿐이다**: "꿈 맥락을 아는 사주"(§4-A ①). 142편 꿈 콘텐츠 보유자만 가능. 나머지(용어 없음·입력 마찰·무료)는 실행력 문제이지 해자가 아니다
- **사주는 신규 유입 수단이 아니라 리텐션 도구다.** 사주 시장은 레드오션
- **이동을 요구하는 설계는 실패한다** — 세션당 1.26에서 "다음 페이지로 가세요"는 작동하지 않음이 0건으로 증명됨. 결합은 **꿈 페이지 안에서 완결**되어야 함(인라인 설계, `docs/handoff/DEV.md` §5-2)

### 보류 (이유 있음, 재논의 전 이 항목 먼저 읽을 것)
| 항목 | 보류 이유 |
|---|---|
| 유료화(결제) | 전제(사업자등록·통신판매업) 충족. 그러나 현 트래픽 유료전환 1% = **월 4.5만 원** → 구축비 회수 불가. **일 500명 전 보류** |
| 카카오톡 일일 발송 | 비용은 감당 가능(알림톡 7~14원). 문제는 **백엔드·계정·전화번호 수집**이 필요하고 생년월일 서버 저장이 §4-A ④ "서버 미저장" 약속과 충돌 |
| 타로·이름궁합 이식 | 둘 다 단일 HTML. **꿈과 연결점이 없어 해자에 기여하지 않음.** 재사용 부품만 유효: 이름궁합의 생년월일 입력 → 사주 궁합, 타로의 공유카드 생성기 |
| 젊은 층 타깃 톤 변경 | 기각(`DECISIONS.md` 09-02). 사용자층 30~50대 추정, 신규 획득이 필요한 전략이라 가장 약한 영역 |

## 5. 세 창에 지시하는 방법
결정이 나면 **해당 창의 핸드오프 "대기 작업" 절에 항목을 추가**하고, 운영자가 그 창에 알린다.

| 지시 대상 | 파일 | 절 |
|---|---|---|
| 개발 | `docs/handoff/DEV.md` | §5 대기 작업 |
| 데이터 | `docs/handoff/DATA.md` | §8 대기·판단 사항 |
| 컨텐츠 | `docs/handoff/CONTENT.md` | §5 다음 일 |

지시에는 **왜(근거 수치)**를 함께 적는다. 근거 없는 지시는 그 창에서 다시 판단하게 되어 시간이 두 배로 든다.
