## §1. 합의된 기획 (우선순위순)

### P0 패키지 — 지금 당장. 내부 순서 고정: ①→②→③

**① 계측 + 검색엔진 등록 배포 (D0)**
- GA4 커스텀 이벤트 7종: `dream_search`(keyword, result_count) / `haemong_start`(source, keyword) / `lucky_view`(keyword, fallback) / `share_click`(method, page_type) / `related_click`(from, to) / `cta_lucky_click`(dream) / `saju_open`(entry_point). 전 페이지 공통 스니펫 1개.
- 재방문 측정은 GA4 기본 신규/재방문 지표가 주지표. localStorage 기반 감지는 days_since_last 보조 파라미터로만.
- **네이버 서치어드바이저 등록·소유확인(정적 파일 1개)·sitemap 제출 + Daum 검색등록.** 한국어 꿈해몽 검색은 네이버 비중이 구조적으로 높음 — Search Console만으로는 시장 절반을 못 본다.

**② 기준선 수집 (3~7일, 상한 7일 — 수리 지연 금지)**
- 수리 전 "얼마나 새는지"(CTA 클릭 후 이탈, 404 도달)를 측정해 개선 폭 증명의 기준선 확보.

**③ 회유 루프 수리 배포 (D+3~7)**
- **CTA 링크 재설계**: 139개 dream 페이지의 "행운번호 받기" CTA를 `index.html?kw=뱀꿈&cat=wealth` 형태로 일괄 치환. 링크가 데이터를 운반하므로 별도 매핑 테이블 불요. index.html은 kw를 입력창에 채우고 해몽+번호 자동 실행.
  - 배경(코드 검증 사실): 현 CTA는 `?dream=영문슬러그`인데 index.html에 파라미터 처리 코드 0줄. 해몽 엔진은 한글 키 기반이라 슬러그 전달만 복원해도 139개 대부분이 동일한 범용 결과로 떨어짐.
  - `cat` = 폴백 카테고리 8종(wealth/change/warning/relation/delay/anxiety/achieve/protect). dreamDB 미커버(139개 중 약 100개) 시 해몽문은 "『키워드』+카테고리 템플릿" 조립, 번호는 kw 문자열을 기존 `rand(seed)` 시드로 사용해 키워드별 고유 생성. "139개 전부 같은 결과" 금지.
  - 기획 산출물: 139건 kw/cat 지정표(스크립트 추출+검수 반나절), 카테고리 템플릿 8문안.
  - **§2-1의 보안·인코딩 요건 준수 필수.**
- **깨진 내부링크 58종(상대39+절대19) 수정 + canonical 정리**: canonical "자기 자신"은 아래 판정표 승자에 한함.
- **중복 7쌍 판정표(잠정, canonical은 가역)**: 통합 4쌍 — card-payment-fail→**failed**, email-send-failed→**not-sent**, golden→**gold**, fire-dream→**fire** (패자 canonical→승자 + 내부링크 교체). 유지 3쌍 — mirror쌍/phone-battery쌍/alarm쌍은 실제 다른 꿈 상황이라 title 차별화+상호링크만. (14개 파일 실존 검토자 확인 완료)
- **sitemap 42개 누락 보강**, changefreq 실태 일치화(index=daily, dream=weekly), 고아 페이지 6개 guide.html 연결.
- **동일 치환 패스 편승**: viewport `user-scalable=no` 제거(접근성 위반 수정), 중복·유지 쌍 title 차별화. 139개 파일은 한 번만 연다.
- 성공지표: `cta_lucky_click`→`lucky_view` 도달률 80%+, 홈 404 클릭 0, fallback 노출 비율.

**④ AdSense 수리 (§4-8 사용자 확인 즉시, 병행)**
- 현황: 스크립트는 index·guide에 로드되나 index 광고 유닛 0개 — 로드 비용만 내고 수익 0.
- 분기: 계정 승인됨 → index에 유닛 배치(AdFit 지면 경합 없는 위치, 페이지당 광고 슬롯 총량 현행 3개 상한 유지) / 심사 중·거절 → 스크립트 정리 + 중복 통합을 심사 대비 품질 작업으로 선행.

### P1 — 루프 강화 (P0 배포 후 착수)

1. **서버사이드 회전 (매일 자동 업데이트의 실체)**
   - index.html "오늘의 꿈 3선+오늘의 한 줄": GitHub Actions cron이 매일 마커 주석(`<!--TODAY:START/END-->`) 사이를 실제 리라이트 후 커밋 → Vercel 자동 배포. 사용자와 크롤러가 같은 신선도를 봄. changefreq daily가 정직해짐.
   - dream 139개 "오늘 알아볼만한 꿈" 그리드: 주 1회 일괄 리라이트(디프 소음 회피, changefreq weekly와 정합).
   - sitemap lastmod는 실제 변경 파일만 갱신.
   - 실행 방식·한도 검증 완료: §2-2 참조.
2. **내 꿈 서랍 (localStorage)**: 해몽 시 {날짜, 키워드, 번호} 자동 저장 → 재방문자 홈 상단 "지난번 ○○꿈 번호 다시 보기". 토요일 로또 추첨일 전후 강조로 주간 재방문 리듬화. manifest.json 1개로 "홈 화면 추가" 안내.
3. **공유 실질화**: dream 페이지에 Kakao SDK 로드해 진짜 카카오 공유 전환(현재는 SDK 미로드로 사실상 링크복사, 코드 검증) + 키워드군별 정적 OG 이미지 10~20종(현재 전 페이지 0건) + 공유 문구에 결과 포함 + `?utm_source=share_kakao` 부착.

### P2 — 사주 결합 리포트 (신규 재방문 기둥)

- 포지셔닝: 단독 사주 앱과 경쟁하지 않고 "이 꿈 × 내 사주" 결합 리포트. 진입점 3종(해몽 결과 하단 / dream 페이지 2차 CTA / 재방문자 원탭).
- 콘텐츠: 일간 10 × 카테고리 8(=P0 폴백 8종 재사용) = 80조합 + 일진 천간 수식 단문 10문안 = 총 90문안. "매일 다름" = 일진 단문+일별 번호·강조점 변동. 공수 4~6일(LLM 초안+전량 사람 검수).
- 입력: 생년월일만 필수(select 3개), 시간 "몰라요" 허용, localStorage 저장·전송 없음(개인정보처리방침 갱신). 만세력은 클라이언트 계산(0원).
- v1은 전면 무료+광고. 유료는 데이터 확보 후 외부 링크형만 검토(자체 결제 금지).
- 사주→꿈 역회유("오늘 꾸면 좋은 꿈 3선")로 상호 재방문 구조: 사주=매일 주기, 꿈=유입.

### P3 — 신규 페이지 파이프라인 (데이터 확인 후)

- 주 3~5개(매일 양산 금지 — thin content·카니벌라이제이션 재발 방지), 월 1회 배치 검수 큐 + Actions cron 배포.
- 주제 선정: `dream_search`의 result_count=0 검색어(찾았는데 없는 꿈) 월 1회 추출 — 사용자 수요가 편집 계획이 되는 0원 구조.
- 착수 조건: §4-2 페이지별 실적 확인. 하위 페이지 유입 0이면 생성보다 기존 개선 우선.

## §2. 검토자 직권 결정 사항 (최종 라운드 종결 조치)

### 2-1. `?kw=` 설계의 보안·인코딩 요건 (쟁점 1 조건부해소의 조건 — 구현 필수 요건으로 확정)

1. **반사 XSS 차단**: `kw`는 URL로 들어오는 사용자 제어 값이고, index.html은 innerHTML을 13곳에서 사용 중(코드 확인). kw를 화면에 넣을 때는 **textContent(또는 전면 이스케이프)만 허용**, innerHTML 경로에 kw 원문 삽입 금지. `cat`은 **8종 화이트리스트 검증** 후 불일치 시 기본값(change) 처리.
2. **인코딩 명기**: 139개 CTA 치환 시 kw는 `encodeURIComponent` 된 형태로 기록(한글 원문 URL은 일부 인앱브라우저·복사 경로에서 깨질 수 있음). index 측은 `URLSearchParams` 파싱(자동 디코드) 사용.

### 2-2. 서버사이드 리라이트 실행 방식 확정 (쟁점 2 실행 가능성 점검 결과)

- **확정 방식: GitHub Actions cron → 마커 사이 HTML 리라이트 → git commit → Vercel이 정적 파일 자동 재배포.** 이것은 빌드 타임 텍스트 치환이므로 **vercel.json rewrite나 Edge Middleware가 전혀 필요 없다** — 정적 사이트 + Vercel 무료 플랜 제약과 완전히 호환되며, Vercel 쪽 설정 변경 0건. (Edge Middleware/서버 함수 안은 "정적·0원" 전제에서 검토 가치 없음 — 채택하지 않는다.)
- 한도: Actions는 public repo 무료, private도 월 2,000분(본 워크로드는 월 수십 분). Vercel Hobby 일 배포 한도(100회) 대비 일 1회 — 여유.
- **운영 주의 2건(워크플로 요건에 포함)**: (a) cron은 정시 실행이 보장되지 않고 수십 분 지연 가능 — "오늘의 꿈" 갱신 시각을 트래픽 낮은 새벽(KST 04~05시)으로 잡을 것. (b) GitHub는 60일간 저장소 활동이 없으면 예약 워크플로를 자동 비활성화함 — 본 설계는 워크플로 자체가 매일 커밋하므로 통상 문제없으나, 파이프라인 중단 시 연쇄 정지되므로 **"오늘의 꿈 날짜 표기가 오늘인지"를 주 1회 눈으로 확인**하는 1분짜리 점검을 운영 루틴에 명기.

### 2-3. 중복쌍 잠정 판정의 재검토 일정 고정 (쟁점 4)

- 통합 4쌍의 canonical 조치는 즉시 시행하되, **서치어드바이저·GSC 데이터 확보 90일 후 1회 재판정**(승자 교체 또는 유지 확정)을 일정으로 고정한다. canonical은 가역이므로 리스크 없음. 재판정 기준: 쌍별 검색 노출·클릭 합산에서 패자 페이지가 승자보다 유의하게 높으면 방향 교체.

### 2-4. 문안류 산출물의 검수 책임 일원화

- kw/cat 지정표 139건, 카테고리 템플릿 8문안, 사주 90문안 — 전부 "LLM 초안 + 운영자 전량 검수" 원칙(§2-2 v2 원칙을 전 문안류로 확대 적용). 무검수 게시 금지.

## §3. 활성화 기여 Top 5 (기여 큰 순)

1. **회유 루프 수리(P0-③)** — 139개 랜딩의 메인 CTA가 현재 "빈 화면", 홈 위젯이 404인 상태의 손실 복구. 모든 후속 시책이 이 루프 위에서 돌므로 기여가 아니라 전제이자 최대 레버리지.
2. **네이버 서치어드바이저·Daum 등록(P0-①)** — 한국 꿈해몽 검색의 주 전장이 네이버인데 현재 구글 축만 관리 중. 반나절 작업으로 미개척 유입 채널 전체가 열리는 유일한 항목.
3. **공유 실질화(P1-3)** — 해몽·행운번호는 카톡 공유 친화 소재인데 현재 공유가 사실상 링크복사+미리보기 빈약. 진짜 카카오 공유+OG 이미지는 유일한 무료 신규 유입 루프(검색 외).
4. **서버사이드 회전(P1-1)** — "올 때마다 다른 첫 화면"을 사용자와 크롤러 모두에게 실제로 제공 — 재방문 사유와 크롤 신선도 신호를 동시에 만드는 0원 무인 장치.
5. **내 꿈 서랍 + 토요일 리듬(P1-2)** — 로또 소재에 내재한 "번호 받기→추첨 확인" 주 1회 주기를 재방문으로 전환하는 최초의 리텐션 장치(현재 localStorage 사용 0건). ※사주(P2)는 잠재 기여는 크나 공수 최대·가설 단계라 Top 5에서는 제외, `saju_open` 검증 후 승격 후보.

## §4. 사용자 확인 필요 항목

1. GA4 최근 90일 일별 사용자·세션 (전체 규모)
2. 페이지별 조회수 상위 20 + 하위 30 (P3 착수 판단: 생성 vs 기존 개선)
3. 세션 소스/매체 — 특히 naver vs google vs daum 비중
4. 재방문자 비율·평균 세션 시간·세션당 페이지수 (루프 기준선)
5. `memimo_click` 실적 (기존 유일 이벤트 = 현행 CTA 기준선)
6. Search Console: 노출/클릭, 상위 쿼리, 색인 제외 페이지 수
